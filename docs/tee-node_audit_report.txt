1. Executive Summary

Overall code quality is mixed: the repository shows substantial functionality and non-trivial architecture, but several auth, secret-management, and deployment paths still look unsafe or incomplete for production use.

Most serious risks:

A committed private key is present in the repo: hack/build/keys/private.pem (line 1).
Public authConfig appears to expose SMTP and OAuth client secrets through GraphQL: graph/auth.graphqls (line 177), graph/auth.resolvers.go (line 531).
Secret upload/init flows authorize only “valid token”, not “token owner matches target user”, enabling cross-user actions: graph/secret.resolvers.go (line 25), graph/auth.go (line 22).
API-key expiry checks are inconsistent; signing paths may accept expired locally stored API keys: graph/resolver.go (line 28), graph/auth_helpers.go (line 60).
Runnable/testable status:

The project does not appear self-contained.
go test ./... could not be executed here because go.mod (line 3) requires go 1.26.3, and the environment attempted a toolchain download that failed with “operation not permitted”.
Startup also depends on local runtime data and keys under ./token_chain_data/...: main.go (line 52), main.go (line 107).
High-priority areas to review first:

GraphQL auth and config exposure
Secret-management flows
Wallet/signing token validation
Runtime/deployment assumptions
Consensus/store atomicity TODOs
Observed test footprint:

There are 49 *_test.go files in the repository, but I could not execute them due the Go toolchain issue.
2. Potential Bugs

High: Recovery flow generates an OTP but never delivers it to the user.
File: graph/auth.resolvers.go (line 355)
Function: RequestRecovery
Description: The resolver creates and stores an OTP, then immediately returns success, but never sends email or otherwise returns the code.
Why it may fail: Real users cannot complete recovery without out-of-band access to storage/logs.
How to reproduce: Call requestRecovery, then attempt verifyRecovery; the user never receives the OTP.
Severity: High
Suggested fix: Reuse the email service used by RequestOtp, or explicitly document and implement the intended delivery channel.

High: Signing API may accept expired API keys from local storage.
File: graph/resolver.go (line 28)
Function: ResolveSignerEmail
Description: Local API keys are accepted if IsActive is true, but ExpiresAt is never checked.
Why it may fail: Expired keys may still authorize signTransaction and signMessage.
How to reproduce: Create a local token via createUserAPIKey, let it expire, then call signing mutations using that token.
Severity: High
Suggested fix: Reuse resolveEmailFromToken() or add explicit IsExpired() checks in ResolveSignerEmail.

High: Recovery OTP is predictable.
File: graph/auth.resolvers.go (line 356)
Function: RequestRecovery
Description: OTP is derived from time.Now().UnixNano()%1000000.
Why it may fail: It is predictable enough for brute-force or timing attacks, especially without strong rate limiting in this flow.
How to reproduce: Observe server timing and approximate the 6-digit space around the call time.
Severity: High
Suggested fix: Use cryptographically secure random generation like the OTP service already does in pkg/services/auth/otp.go (line 197).

Medium: OTP verification ignores clientID even though generation stores it.
File: graph/auth.resolvers.go (line 35), pkg/services/auth/otp.go (line 52), pkg/services/auth/otp.go (line 102)
Function: VerifyOtp, OTPService.Verify
Description: OTPs are generated with clientID but verified only by email + OTP.
Why it may fail: A code intended for one client/app context may be replayed against another.
How to reproduce: Generate OTP with one clientId, verify with another.
Severity: Medium
Suggested fix: Bind verification to the stored clientID, or remove it entirely from the API contract.

Medium: GraphQL auth directive can panic when context lacks a token.
File: graph/auth.go (line 22)
Function: AuthCheck
Description: ctx.Value(...).(*store.GatewayTokenInfo) does an unchecked type assertion.
Why it may fail: If middleware is bypassed or reused incorrectly, the server will panic instead of returning an auth error.
How to reproduce: Invoke a directive-protected resolver without AuthMiddleware populating context.
Severity: Medium
Suggested fix: Use the two-value type assertion and return a normal GraphQL auth error.

Medium: DistributeMiddleware can panic on malformed model JSON types.
File: pkg/api/gateway/auth_middleware.go (line 60)
Function: DistributeMiddleware
Description: bodyMap["model"].(string) assumes the field is always a string.
Why it may fail: A numeric/object model value causes panic.
How to reproduce: POST a JSON body like {"model":123} to a /v1/... relay route.
Severity: Medium
Suggested fix: Type-check before assertion and return a 400 error for invalid shape.

Medium: Relay handler ignores JSON unmarshal errors.
File: pkg/api/gateway/relay_handler.go (line 69)
Function: HandleRelay
Description: json.Unmarshal(bodyBytes, &reqBody) error is discarded.
Why it may fail: Invalid bodies may continue into upstream relay logic with partially zeroed fields.
How to reproduce: Send malformed JSON to relay endpoint.
Severity: Medium
Suggested fix: Reject malformed JSON before routing upstream.

Medium: Per-process RSA key breaks secret usability across restarts.
File: graph/mod.go (line 27), graph/secret.resolvers.go (line 156)
Function: package init, SecretRsa, UploadSecret
Description: The RSA keypair is generated in memory at process start and never persisted.
Why it may fail: Clients encrypting with /secret_rsa before a restart cannot have those payloads decrypted after restart.
How to reproduce: Fetch secret_rsa, encrypt a payload, restart server, then try upload_secret.
Severity: Medium
Suggested fix: Persist the RSA keypair securely, or explicitly make the key ephemeral and rotate with a versioned client flow.

Medium: First-time password setup stores client-supplied hash directly and compares it verbatim later.
File: graph/auth.resolvers.go (line 123), graph/auth.resolvers.go (line 155)
Function: SetPassword, VerifyPassword
Description: The backend stores passwordHash as provided and later compares equality directly.
Why it may fail: Security semantics depend entirely on client behavior; format/version drift is brittle, and weak client hashing is unrecoverable server-side.
How to reproduce: Change client hashing logic or send inconsistent encodings.
Severity: Medium
Suggested fix: Define a strict server-side password-verification contract with versioning and validation.

Medium: Wallet login appears replayable.
File: graph/auth.resolvers.go (line 421), graph/auth_helpers.go (line 105)
Function: LoginWithWallet, verifyEIP191Signature
Description: Login validates an arbitrary signed message but does not bind it to a server-issued nonce or freshness window.
Why it may fail: Replayed signatures can log in again if the same message is reused.
How to reproduce: Re-submit a previously valid (address, signature, message) tuple.
Severity: Medium
Suggested fix: Issue one-time nonce/challenge messages and verify freshness/used-state server-side.

Medium: REST blockchain token endpoint is exposed but unimplemented.
File: graph/rest_handler.go (line 8)
Function: RegisterRESTRoutes
Description: /api/blockchain/token always returns “not yet implemented”.
Why it may fail: Client SDKs depending on this route will fail at runtime.
How to reproduce: POST to /api/blockchain/token.
Severity: Medium
Suggested fix: Hide/disable the route until implemented, or implement contract/order verification.

Medium: Consensus-related store cleanup is explicitly non-atomic.
File: tee-chain/tx_finalize.go (line 68), tee-chain/tx_prepare.go (line 138)
Function: FinalizeBlock path, proposal preparation path
Description: Comments acknowledge deletion of tx index/signature state outside block transaction / before commit.
Why it may fail: Rollbacks can leave index/signature state inconsistent with committed chain state.
How to reproduce: Trigger rollback/failure between cleanup and block commit.
Severity: Medium
Suggested fix: Move these deletions into the same transactional/commit-safe phase.

Low: Server start ignores returned errors from ListenAndServe and ListenAndServeTLS.
File: graph/mod.go (line 95)
Function: StartServerWithResolver
Description: The server logs and calls ListenAndServe* without checking the returned error.
Why it may fail: Port conflicts or TLS cert issues can terminate startup silently relative to main flow.
How to reproduce: Occupy the configured port or remove TLS files with partial config.
Severity: Low
Suggested fix: Capture and log/fail on returned errors.

3. Security Risks

Critical: Private key committed to the repository.
File: hack/build/keys/private.pem (line 1)
Description: A PEM private key is committed in plaintext.
Risk: Immediate secret exposure, impersonation risk, possible downstream compromise if reused anywhere.
Suggested fix: Revoke/rotate the key immediately, remove it from version control, scrub history if necessary, and add secret scanning.

Critical: Public GraphQL config query appears to expose secrets.
File: graph/auth.graphqls (line 177), graph/auth.resolvers.go (line 531)
Description: Public authConfig returns smtpPassword, googleClientSecret, githubClientSecret, and twitterClientSecret. The comment says “已脱敏”, but the resolver returns those fields directly.
Risk: Full credential disclosure to unauthenticated callers.
Suggested fix: Remove secret fields from the public schema and ensure AuthGetPubConfig cannot leak them.

High: Secret-management mutations allow authenticated users to target arbitrary user addresses.
File: graph/secret.resolvers.go (line 25), graph/secret.resolvers.go (line 86), graph/auth.go (line 22)
Description: upload_secret and init_disk_key only require a valid API key; they do not verify that the token owner is authorized for the supplied user.
Risk: Cross-user secret poisoning or unauthorized disk-key initialization.
Suggested fix: Bind the mutation target to the authenticated principal, or add explicit ownership/authorization checks.

High: Overly permissive credentialed CORS.
File: graph/mod.go (line 49)
Description: AllowedOrigins allows https://* and http://* with AllowCredentials: true.
Risk: Cross-origin authenticated access from arbitrary origins if browsers accept the resulting policy; even where library behavior narrows this, the intent is unsafe.
Suggested fix: Use a strict allowlist of known frontends and avoid wildcard origins with credentials.

High: Auth config mutation lacks schema-level auth protection.
File: graph/auth.graphqls (line 137), graph/auth.resolvers.go (line 437)
Description: setAuthConfig has no @AuthCheck; authorization relies on deeper behavior in contract calls, if any.
Risk: Misconfiguration or unauthorized secret changes if contract-side enforcement is incomplete or bypassable.
Suggested fix: Add explicit auth/role checks at the API layer in addition to contract-level protection.

High: Password-related user data is asynchronously written in plaintext JSON to chain storage.
File: graph/auth.resolvers.go (line 146)
Description: SetPassword marshals the full AuthUser and stores it via AuthStoreAuthUser.
Risk: If AuthUser includes PasswordHash, Salt, and DKHash, those become chain-stored sensitive material.
Suggested fix: Store only the minimal non-secret fields on chain, or encrypt sensitive profile data before persistence.

Medium: Panic details are returned to clients.
File: pkg/api/gateway/middleware.go (line 19)
Description: Recovery middleware returns panic: <message> in the response body.
Risk: Internal error details leak to callers and aid exploitation.
Suggested fix: Log internals server-side and return a generic 500 message.

Medium: SMTP “STARTTLS” path does not explicitly enforce STARTTLS.
File: pkg/services/auth/email.go (line 132)
Description: sendViaSTARTTLS just calls smtp.SendMail, which may not guarantee explicit STARTTLS behavior as the function name implies.
Risk: Misconfigured mail delivery could occur without transport guarantees the code comments imply.
Suggested fix: Perform explicit SMTP handshake and STARTTLS negotiation, or rename the method to avoid false security assumptions.

Medium: Missing body size limits on API requests.
File: pkg/api/gateway/auth_middleware.go (line 52)
Description: Relay middleware eagerly reads the full body without a size cap.
Risk: Memory pressure / DoS via oversized request bodies.
Suggested fix: Apply http.MaxBytesReader or equivalent per route.

Medium: No obvious unsafe shell execution found.
Checked: repo-wide search for exec.Command, os/exec, shell invocations returned no matches.
Note: This is a positive finding.

Medium: No obvious SQL injection surface found.
Checked: the project primarily uses Pebble KV storage rather than SQL.
Note: This is a positive finding, but it does not reduce the auth/secret risks above.

Medium: Dependency vulnerability scan not completed.
Reason: I could not run Go-based audit tooling because the required toolchain in go.mod (line 3) could not be fetched in this environment.
Suggested fix: Run govulncheck and dependency scanning in CI using the intended Go toolchain.

4. Runtime and Deployment Issues

High: Toolchain version mismatch blocks local testing and likely affects CI portability.
File: go.mod (line 3)
Description: The module requires go 1.26.3, which was not available locally; go test ./... attempted to download it and failed.
Impact: The project is not trivially testable unless CI/build hosts support automatic toolchain download for that exact version.
Suggested fix: Pin to a released/available Go version and document it in the README.

High: Main-chain config defaults appear invalid for main.
File: config/main.go (line 8)
Description: Urls is []string{""} and key addresses are empty.
Impact: CHAIN_ENV=main looks non-runnable without additional out-of-band configuration.
Suggested fix: Provide a real production config path or fail fast with explicit configuration validation.

High: Hardcoded runtime file paths required at startup.
File: main.go (line 52), pkg/store/db.go (line 18), graph/mod.go (line 95)
Description: Startup depends on relative paths under ./token_chain_data/... for validator keys, DB, and TLS certs.
Impact: Running from the wrong working directory or with missing bootstrap files will fail.
Suggested fix: Externalize paths to configuration and validate them on startup.

Medium: LoadConfig comment and behavior diverge.
File: pkg/api/auth/config.go (line 40)
Description: Comment says “fallback to environment variables”, but implementation just returns &AuthConfig{}.
Impact: Operators may believe env vars are honored when they are not; services may silently run with empty secrets and mock behaviors.
Suggested fix: Either implement env loading or update the comment and startup validation.

Medium: Empty auth config weakens deterministic wallet/key derivation.
File: pkg/services/wallet/derive.go (line 34), pkg/services/wallet/derive.go (line 67)
Description: SeedSecret and JWTSecret come from config; if config is empty, seed derivation and server key wrapping become deterministic from email alone or near-empty material.
Impact: Weak or predictable key material in misconfigured deployments.
Suggested fix: Refuse to start if required auth secrets are absent.

Medium: Server startup path uses debug runtime loading in main.
File: main.go (line 107)
Description: LoadRuntimeForDebug() is called in normal startup.
Impact: Suggests debug-mode behavior may be coupled to production startup.
Suggested fix: Separate debug and production runtime loading paths.

Low: No graceful HTTP shutdown path visible.
File: main.go (line 150), graph/mod.go (line 36)
Description: BFT node shutdown is handled, but the HTTP server is launched in a goroutine without a shutdown handle.
Impact: In-flight API requests may be dropped on process termination.
Suggested fix: Use an http.Server with context-based shutdown.

5. Testing and Reliability

Tests exist, but I could not run them because of the Go toolchain requirement in go.mod (line 3).
High-risk auth/security flows do not appear obviously covered by enforcement tests from the inspected code paths:
secret ownership checks
API key expiry on signing
wallet-login replay protection
authConfig secret redaction
recovery OTP delivery and brute-force resistance
Several areas show fragile error handling:
ignored errors from crypto and random generation: graph/auth_helpers.go (line 22), pkg/services/wallet/derive.go (line 72)
ignored json.Unmarshal in relay flow: pkg/api/gateway/relay_handler.go (line 69)
async goroutine writing auth state without retry/observability: graph/auth.resolvers.go (line 146)
Rate limiting is in-memory and keyed by RemoteAddr: pkg/api/gateway/middleware.go (line 128)
This is fragile behind proxies, resets on restart, and may punish many users behind one NAT while allowing easy bypass in distributed abuse.
OTP anti-abuse state is partly in-memory: pkg/services/auth/otp.go (line 18)
Restarting the process clears some counters and send history.
6. Code Quality Improvements

Unify token validation logic.
resolveEmailFromToken() and ResolveSignerEmail() currently implement different rules. Centralizing this would remove expiry/auth drift.

Add explicit configuration validation at startup.
Missing chain URLs, secrets, TLS files, and runtime assets should fail fast with actionable errors rather than silently degrading.

Reduce hidden global state.
Global teeChain and rsaKey in graph/mod.go (line 24) make lifecycle and restart behavior harder to reason about.

Separate public vs sensitive config models.
The current GraphQL config contract mixes public metadata with secret fields and depends on comments rather than type separation.

Improve error handling discipline.
There are several ignored errors in crypto/random/JSON paths that should be explicit.

Add request size and timeout controls.
The HTTP server and middleware stack should define body-size caps, read/write timeouts, and upstream timeouts.

Clarify deployment documentation.
The README is architectural, but it does not clearly document required Go version, required token_chain_data files, TLS expectations, or config bootstrap.

Review async write patterns.
The goroutine in SetPassword can lose errors and race with subsequent reads; persistence should be observable and consistent.
